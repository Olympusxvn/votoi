# VOTOI Audit Report - 2026-11-04

Self-audit by Muse (not a third-party audit). Scope: the VOTOI codebase,
README, landing page, and live demo state, checked against every public
claim the project makes to judges. Method: code read, live smoke tests
against a local server on PORT 3101, a read-only database check, a
repository-wide secret scan, and independent onchain verification via the
Sui public GraphQL endpoint. No payments were sent, no keys were rotated,
and no state was left degraded: the server was stopped and test artifacts
cleaned after the run.

Main branch head when the audit started: `bfd1baf6f42927b12a74b85960924d7b01b0e138`
(Nov 4 push of `src/server.ts`, `app/src/App.tsx`,
`docs/ai-builder-prompts.md`, `README.md`). During the audit, the user added
commit `087f522ba71c95994604510b77aeaadd79f100df` via the GitHub web UI
("Expand README with project pillars and payment details"): the Two Pillars
summary, placed before "Verify it in 60 seconds". That edit was read back
and checked: it matches the audited claims and adds no new claim, so the
findings below stand unchanged. This report is pushed on top of `087f522`.

## Verdict

PASS, with findings. No blocking safety issue was found: money cannot move
above the cap, facts cannot carry em-dashes, receipts are never credited
with a Walrus blob they do not have, and no secret was found anywhere in
the tree. Five findings follow, all low severity except one demo-visibility
gap (F3). Known limitations from the README remain accurate and unchanged.

## Verified claims

- **12 facts, 12 blobs.** `GET /api/health` returned `factsCached: 12`,
  `walrusBlobsCached: 12` before and after the wipe test, and
  `GET /api/facts` returned a list of 12. Relayer: healthy.
- **Wipe and rehydrate.** `POST /api/test/wipe-cache` returned
  `wiped: true, factsRestored: 12, degraded: false`, and health after the
  wipe was again 12/12. The flagship memory claim is proven live, not just
  documented.
- **Settled payment.** The database holds exactly one payment row: 0.01
  USD, status `settled`, digest
  `BDFfAHCMFFNnk5ERmBxqndZvin7NTTXXxPHJgUsFudrh`, created 2026-10-21.
  The Sui public GraphQL endpoint independently confirms that digest:
  status `SUCCESS`, sender `0xb33fcc35268837f0ff46a299703f15ab65923717805edfb253295cbee1d1d6e0`
  (the recorded allowance spender). The Suiscan page itself is
  JavaScript-rendered and returned no extractable text to an automated
  fetch, so GraphQL was used as the independent check; the Suiscan link
  in the README and landing page still resolves for a browser user.
- **50 USD cap, enforced three ways.** Database CHECK
  `agent_payments_cap_50_usd` (`total_usd <= 50.00`), code caps
  `AGENT_PAYMENT_CAP_USD = 50` and `SPLIT_PAYMENT_USD_CAP = 50.0`, the
  `HumanApprovalRequired` throw, and the chat path that records over-cap
  payments as `awaiting_approval` instead of sending them.
- **Em-dash ban, enforced three ways.** The serializer replaces em/en
  dashes and throws if a serialized fact still contains one, and
  database CHECKs cover `learned_facts` and `pending_writes`. README and
  landing page contain zero em-dash characters.
- **Citations.** A deterministic chat answer ("What do you know about my
  coffee habit?") returned exactly 3 citations: dining out, Highlands
  Coffee, Circle K. The LLM path returns no citations by design, and no
  LLM key is configured in `.env`, so the deterministic path is the one
  judges will hit.
- **Receipts never fake a blob.** `POST /api/receipts` queued a test
  receipt; `GET /api/receipts/:sha` returned `status: queued`,
  `blobId: null`, `merchant: null`, `amountUsd: null` (no invented
  values), and an unknown sha returned 404. Re-verified today.
- **Revoke is honestly 501.** `POST /api/allowance/revoke` returned HTTP
  501 with an error message that states revocation is not wired and why.
  Re-verified today.
- **Health never burns Tatum credit.** `GET /api/health` reads only the
  local cache and carries a gateway note dated 2026-11-04. `GET
  /api/status` degrades honestly while chain reads are unavailable:
  `chainReadsUnavailable: true` with empty allowance fields, not invented
  numbers.
- **API table matches code.** All 10 routes in the README table exist in
  `src/server.ts`: health, status, facts, payments, chat, wipe-cache,
  allowance/build, allowance/revoke, receipts POST, receipts by sha.
- **No overclaims.** README and landing page were scanned for payroll,
  stablecoin, merchant rails, fully autonomous, and guaranteed. The only
  matches are negations ("never through an escrow or a custodial
  balance"). The x402 wording is accurate: payment rows carry
  `standard: "x402"` in code, and the flow is approval-gated; the project
  does not claim a full x402 facilitator protocol.
- **Durable writes.** `recoverPendingWrites()` resubmits via deterministic
  idempotency keys, finalizes on done-plus-blob, and drops dead writes
  for recompute on the next pass. See F2 for the scheduling caveat.
- **Secret scan clean.** A full-tree scan (excluding `node_modules`,
  `.git`, `dist`, and `.env*`) for private-key and API-key patterns
  returned 0 matches. `.env` is gitignored (`.gitignore` line 3), the
  farm results file contains 0 key-pattern matches, and the Nov 4 push
  manifest contained exactly 4 files, no `.env`.

## Findings

### F1 (LOW): chat latency is not guaranteed under 2 seconds

Three timed calls of the same deterministic question measured 2.32s
(cold), 2.51s (warm), and 1.14s (warm). The README wording "Chat stays
under 2 seconds" therefore holds usually, not always. No LLM key is
configured, so the variance is hosted-database latency, not the 1500ms
LLM timeout. FIXED 2026-11-04: the README now says chat answers from
cache "typically within 2 seconds".

### F2 (LOW, documentation precision): compaction recovery is manual, not automatic

`recoverPendingWrites()` runs at the start of every compaction pass
(`runCompactDream` calls it), but passes themselves run only via the
one-off script `scripts/run-compact-once.ts`. The demo server has no
interval and no worker wiring, and `package.json` has no compaction
script. Intents persist durably, so nothing is lost, but "recovery runs"
reads as automatic. Recommendation: one line in the README stating
compaction passes are run via the script, or add a pass trigger. Not
fixed in this audit step.

### F3 (LOW-MEDIUM, demo visibility): the settled payment does not show in the app's Payments panel

The single settled row was keyed under the agent wallet
(`0x5dc5...`), while the app loads payments with the demo wallet
(`0x3ca8...`), so `GET /api/payments` for the default wallet returned 0
rows. The current chat pay path records new payments under the chat
userId, so only this historical Oct 21 row was mis-keyed; the onchain
proof itself is verified (see above) and the README/landing Suiscan link
is valid. FIXED 2026-11-04: the row was re-keyed to the funder wallet
(single-row update guarded by digest plus old userId, verified
afterwards), and `GET /api/payments` for the default wallet now returns
the row: 0.01 USD, status `settled`, digest unchanged.

### F4 (INFO): demo wallet prefill becomes public at the flip

`app/src/App.tsx` defaults the wallet input to the user's personal main
wallet address. That address is public onchain data, not a secret, but
after the Nov 10 public flip it will be visible in source. Flagged for
conscious acceptance; no action required.

### F5 (INFO, corroboration): legacy JSON-RPC is dead on Sui mainnet

The Sui public fullnode now rejects legacy JSON-RPC outright ("Method
not found. JSON-RPC on public fullnodes has been deprecated. Please
migrate to gRPC or GraphQL endpoints."). This independently corroborates
the Tatum gateway 404 as ecosystem-wide deprecation, not a problem with
this project's key, and supports the recorded gRPC/GraphQL direction if
chain reads are ever fixed. No action.

## Known limitations (unchanged, still accurate)

- Tatum Sui gateway returns HTTP 404 for Sui methods with this
  project's key (re-verified 2026-11-04 with a single
  `sui_getChainIdentifier` call). Panels fall back to the local ledger.
- Allowance revocation is not wired (501, see above).
- Receipt OCR is outstanding: no vision provider is configured, and the
  async OCR worker has no caller in the server, so receipts stay queued
  by design. Nothing is faked in the meantime.
- The LLM path returns no citations (sources not attributable); only
  the deterministic path cites facts.
- While chain reads are unavailable, `GET /api/status` cannot confirm
  the production allowance live; the allowance id in the README and
  landing page is a recorded value, not a live-read value.
